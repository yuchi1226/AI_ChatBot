## 1. 概述 (Overview)

本規格書定義了 **AI Agent 核心系統**中，從接收用戶端輸入至發送請求給大語言模型（DeepSeek-V3）之前的關鍵流程。範圍涵蓋 **步驟 1 至 步驟 6**，重點規範「純文字輸入之標準化處理」與「具備 Session ID 之請求封裝機制」。

---

## 2. 輸入前處理模組 (Input Preprocessing Module)

此階段對應流程圖之 **步驟 1 與 步驟 2**。目標是將用戶原始輸入標準化為模型可接受的文字格式。

### 2.1 純文字處理規範 (Plain Text Handling)
若用戶輸入為「純文字」（非檔案），系統需執行以下清理與轉換邏輯：

| 處理項目 | 規格說明 | 預設行為 |
| :--- | :--- | :--- |
| **編碼標準化** | 強制轉換為 UTF-8 編碼，過濾無效的 Unicode 代理對（Surrogate Pairs）。 | 丟棄無法解碼的字元。 |
| **空白字元壓縮** | 將連續的換行符號（`\n`）超過 2 個以上者，壓縮為最多 2 個；將 Tab 符號轉為空格。 | 保留段落結構，移除多餘排版干擾。 |
| **控制字元過濾** | 移除 ASCII 控制字元（如 `\x00` - `\x1F`），保留標準標點符號。 | 僅保留換行（`\n`）與回車（`\r`，於 Windows 環境轉換為 `\n`）。 |
| **長度上限（截斷）** | 若純文字長度超過 **Token 緩衝區預留量**（例如 16,000 Token），啟動智慧截斷。 | 優先保留「尾部」最新內容（因 LLM 通常對結尾記憶較深），並於截斷處插入 `...[前文已截斷]...` 標記。 |

### 2.2 檔案轉換處理 (File Conversion - 補充說明) (暫不實作，僅純文字輸入)
*（雖聚焦純文字，但系統須支援檔案）* 若用戶附加檔案，系統將其轉為 Markdown 格式；若原始內容即為純文字（`.txt`, `.md`），則直接讀入並套用 **2.1 節** 之純文字清理規則。

## 3. 請求建構模組 (Request Construction Module)

此階段對應流程圖之 **步驟 3 至 步驟 6**。目標是封裝一個完整的 API 請求載荷（Payload），並綁定會話狀態。

### 3.1 Session ID 管理機制
Session ID 作為「會話容器」的唯一識別碼，用於掛載歷史對話、系統提示詞緩存與工具授權狀態。

| 項目 | 規格說明 |
| :--- | :--- |
| **取得策略** | 1. 優先讀取 HTTP Header 之 `X-Session-Id`。<br>2. 若 Header 不存在，檢查 Request Body 之 `session_id` 欄位。<br>3. 若皆無，視為**新會話**，由核心調度器生成 UUID v4 並返回給客戶端。 |
| **有效性驗證** | 檢查 Session ID 是否逾時（預設 TTL：30 分鐘無活動即失效）。逾時則視為新會話，並清理緩存之 System Prompt。 |
| **承載資料** | Session ID 必須綁定：<br>- `history`：壓縮後的歷史對話陣列。<br>- `system_prompt_version`：當前使用的系統提示詞版本號（用於 Cache 比對）。<br>- `tool_auth_status`：工具權限狀態（如：是否已授權讀取私人文件）。 |

### 3.2 請求載荷封裝流程 (Payload Assembly)
系統依序執行以下子步驟，完成最終發送至 LLM 的請求：

1.  **步驟 A：注入系統級指令 (System Injection)**
    - 依據模式從「提示詞緩存（System Prompt Cache）」提取對應的 System Prompt。

2.  **步驟 B：結構化提示詞建構**
    - 組合回傳物件，必須包含以下四大區塊：
      ```json
      {
        "role": "系統角色定義 (如: 你是一位專業助理...)",
        "tool_definitions": "[工具呼叫的 JSON Schema 定義]",
        "safety_guardrails": "安全紅線指令 (如: 禁止透露內部思維鏈)",
        "current_datetime": "2026-08-24T00:00:00+08:00 (強制注入當前時間以消除時空模糊)"
      }
      ```

3.  **步驟 C：上下文綑綁 (Context Binding)**
    - 將 **步驟 2** 輸出的處理後文字（或 Markdown 檔案內容）作為本次請求的 `user_query`。
    - 從 Session ID 對應的 Redis / Memory 儲存中拉取 **歷史對話（History）**。
    - 組合最終發送結構（示意）：
      ```json
      {
        "session_id": "a1b2c3d4-...",
        "messages": [
          {"role": "system", "content": "[步驟B組裝的完整 System Prompt]"},
          ... (歷史對話陣列) ...,
          {"role": "user", "content": "[步驟2處理後的純文字輸入]"}
        ],
        "tools": [工具定義清單],
        "stream": true/false,
        "thinking_mode": true  // 開啟深度思考
      }
      ```

## 4. 例外處理與錯誤碼 (Error Handling)

於本階段（步驟 1-6）可能拋出的異常與對應處理：

| 錯誤情境 | HTTP Status | 錯誤碼 | 處理邏輯 |
| :--- | :--- | :--- | :--- |
| **純文字淨長度為 0** | 400 | `EMPTY_CONTENT` | 拒絕請求，回傳「請輸入有效內容」。 |
| **Session ID 格式錯誤** | 400 | `INVALID_SESSION` | 拒絕請求，要求客戶端重新建立會話。 |
| **System Prompt 拉取失敗** | 500 | `PROMPT_FETCH_FAIL` | 啟用 Fallback 預設提示詞（僅基本助理角色），並記錄錯誤日誌。 |
| **歷史對話序列化失敗** | 500 | `HISTORY_CORRUPTED` | 清除該 Session 之歷史紀錄，僅以當前 Query 重試。 |

## 5. 效能規格 (Performance Spec)

為確保核心調度器不造成瓶頸，針對本階段設定以下 SLA：

- **前處理（純文字清理）延遲**：≤ 5ms (P99)。
- **請求建構（含 Session 查詢）延遲**：≤ 10ms (P99)。
- **System Prompt 緩存命中率**：目標 > 99.9%（利用 CDN / 本地記憶體快取）。

---

## 6. 後續串接說明 (Next Steps)

完成本階段（步驟 6）後，核心調度器將把建構完成的完整 Prompt 發送至 **LLM 推理引擎**，並進入流程圖後續之 **步驟 7（深度思考）** 與 **步驟 11（工具調用決策）** 階段。
