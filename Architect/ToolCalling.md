# 規格書：工具調用判斷模組 (Tool Calling Decision Module)

| 文件版本 | 1.0 |
| :--- | :--- |
| 撰寫日期 | 2026-08-24 |
| 目標框架 | Python Gradio (>= 4.0 / 5.0) |
| 核心目標 | 對應系統流程圖步驟 **⑦**「判斷需要調用工具 (如搜索/讀文件)」 |

---

## 1. 目的與範圍

本模組負責在大語言模型（DeepSeek-V3）完成內部思考（reason_content）後，決定是否需調用外部工具，以及具體調用何種工具、填入何種參數。此判斷直接影響後續工具執行管道的流程，為 Agent 循環（Agent Loop）的關鍵分流點。

---

## 2. 判斷依據

模型應根據以下輸入綜合判斷：

| 輸入來源 | 說明 |
|---------|------|
| 系統提示詞（System Prompt） | 內含可用工具清單、工具描述、使用限制與安全紅線 |
| 歷史對話（History） | 先前已使用的工具及其結果，避免重複無效調用 |
| 當前用戶提問（User Query） | 原始問題及附帶的上下文（如文件內容） |
| 模型內部推理草稿（reason_content） | 模型自我生成的思考過程，包含對問題拆解、資訊缺口分析 |

---

## 3. 工具分類與觸發條件

以下為系統預設支援的工具類型，模型應依條件選擇：

| 工具名稱 | 觸發條件（列舉） | 必填參數 | 選填參數 |
|---------|----------------|---------|---------|
| `web_search` | 用戶問題涉及**即時資訊**、**新聞**、**天氣**、**股價**、**未知事實**，且無內建知識可回答 | `query`（搜尋關鍵詞） | `region`（地區）、`time_range`（時間範圍） |
| `file_read` | 用戶上傳文件（如 PDF、Word、Excel）且問題要求**擷取特定段落**、**統計數據**、**比對內容** | `file_id`（文件識別碼）、`start_page`（起始頁） | `end_page`、`keyword_filter` |
| `code_interpreter` | 用戶要求**執行計算**、**數據分析**、**繪圖**、**模擬**，且需精確數值結果 | `code`（可執行程式碼）、`language`（Python/R） | `input_data`（輸入資料） |
| `database_query` | 問題涉及**結構化數據**（如 SQL 資料庫），需查閱內部知識庫 | `sql_statement` 或 `natural_language_query` | `limit`、`order_by` |
| `file_write` | 用戶要求**生成報告**、**修改文件內容**、**匯出結果** | `file_id`、`content`（新內容） | `append_mode`（是否附加） |
| `http_request` | 需要呼叫第三方 API（如取得天氣 API、翻譯 API） | `url`、`method` | `headers`、`body`、`params` |

> 備註：模型應優先使用**語意匹配**，而非僅靠關鍵詞。例如「今天台北會下雨嗎？」應觸發 `web_search`，而非 `database_query`。

---

## 4. 判斷規則（決策邏輯）

### 4.1 優先級順序

1. **安全紅線優先**：若問題違反政策（如非法內容），則**不調用任何工具**，直接回覆拒絕訊息。
2. **用戶明確指定**：若用戶明確說「請搜尋…」、「幫我讀取某檔案第X頁」，則直接對應指定工具。
3. **知識不足時**：若模型內部推理草稿中標記「未知」、「需查證」，則觸發 `web_search` 或 `database_query`。
4. **計算/分析需求**：若推理草稿包含數值運算、統計描述，觸發 `code_interpreter`。
5. **文件相關**：若用戶上傳文件且問題提及「根據文件」、「文件中的數據」，觸發 `file_read`；若要求修改，則觸發 `file_write`。

### 4.2 單一工具 vs 多工具協作

- 預設情況下，**每次僅調用一個工具**，以避免過度消耗資源。
- 若問題明顯拆解為多個獨立子任務（例如「比較 A 文件和 B 文件的差異，並搜尋相關新聞」），模型可**同時發起多個 tool_calls**（但須在系統提示詞中宣告支援）。

### 4.3 拒絕調用工具的情境

- 問題屬於**常識問答**（如「台灣的總統是誰？」）且模型內建知識可回答（需確認訓練資料截止日期）。
- 問題屬於**主觀意見**或**創意生成**（如「寫一首詩」），無需工具。
- 用戶要求**重複執行**剛完成之工具，且結果未過期（可快取）。

---

## 5. 輸出格式（tool_calls 結構）

當模型判斷需調用工具時，應輸出符合以下 JSON 結構的 `tool_calls` 陣列（即使只有一個工具）：

```json
{
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "web_search",
        "arguments": "{\"query\": \"台北市 今日天氣\", \"region\": \"TW\"}"
      }
    }
  ]
}
```

- `id`：由模型生成唯一識別碼，便於後續結果對應。
- `function.name`：必須為上述工具清單中的名稱。
- `function.arguments`：JSON 字串，必須包含所有必填參數，且數值型態正確。

若無需調用任何工具，則 `tool_calls` 為空陣列或直接省略，並由模型輸出 `content` 最終回覆。

---

## 6. 與其他模組的互動介面

- **輸入**：接收來自核心調度器（Agent Harness）的完整提示（含系統、歷史、使用者輸入及推理草稿）。
- **輸出**：將 `tool_calls` 結構回傳給 Harness，由 Harness 轉送給工具執行管道（Tool Pipeline）。
- **錯誤處理**：若模型輸出的工具名稱不在白名單，或參數型態錯誤，Harness 應觸發**重試機制**（要求模型重新生成 tool_calls），最多 2 次。

---

## 7. 調校與優化建議

| 面向 | 建議 |
|------|------|
| **提示詞工程** | 在系統提示詞中明確描述每個工具的**適用場景**與**範例**，以提高判斷準確率 |
| **Few-shot 範例** | 在對話開頭注入 2~3 組「問題 → 正確 tool_calls」的示例，引導模型學習 |
| **日誌記錄** | 記錄每次判斷結果（含推理草稿摘要），作為後續迭代調校的數據集 | (暫不實做)
| **反饋機制** | 若工具執行結果無法滿足用戶，應允許模型**撤回**並重新選擇其他工具（但次數上限 3 次） | (暫不實做)
